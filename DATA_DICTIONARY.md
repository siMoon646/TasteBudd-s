# Data Dictionary

Reference for every table, column, enum, and constraint defined in [`backend/prisma/schema.prisma`](backend/prisma/schema.prisma). The schema file is the source of truth for structure; this document explains what the data *means* and lists the rules the app enforces that the database does not.

**Keep this in sync:** any PR that changes `schema.prisma` should update this file in the same PR.

## Conventions

- **Database:** PostgreSQL (hosted on Supabase), managed through Prisma.
- **Naming:** Prisma models and fields are `PascalCase` / `camelCase`; the database tables and columns they map to are `snake_case` via `@@map` / `@map`. Both names are listed below.
- **Primary keys:** every table uses a text `id` holding a UUID, generated by Prisma (`@default(uuid())`).
- **Timestamps:** `created_at` defaults to `now()`. `updated_at` is set by the **Prisma client** on every update (`@updatedAt`). It is not a database default or trigger, so writes made outside Prisma do not update it.
- **No soft deletion:** deleted rows are removed, never flagged for deletion.
- **Denormalized counts:** `*_count` columns on `posts` and `comments` are caches of rows in `reactions` / `comments`. The source rows are the truth, and every write that adds or removes a source row must update the matching count in the same transaction (see README → Architecture Notes).
- **Delete behavior:** `Cascade` is used only for structural cleanup that doesn't touch another row's counts. All other foreign keys use Prisma's default, `Restrict`, which makes the database reject a delete that would orphan rows.
- **App-enforced rules:** some rules can't be expressed in the Prisma schema. They are listed under each table and must be validated in the backend before writing.

**Column table key:** *Null?* = column accepts NULL. *PK* = primary key. *FK* = foreign key. *Unique* = single-column unique constraint.

## Enums

### `ModuleType`

The kind of block a `post_modules` row holds. Determines the shape of `post_modules.data`.

| Value | Meaning |
|---|---|
| `text` | Freeform body text |
| `checklist` | List of items that can be checked off (ingredients, steps) |
| `numbered_list` | Ordered list of steps |
| `video` | Embedded video (YouTube only for MVP) |
| `location` | A place pinned to the post |
| `timer` | A cook/prep timer |

### `ReactionType`

The kind of reaction a `reactions` row records.

| Value | Valid target | Meaning |
|---|---|---|
| `like` | post, comment | Positive vote |
| `dislike` | post, comment | Negative vote |
| `save` | post | Bookmark the post |
| `follow` | user | Follow another user |

The "valid target" column is an app-enforced rule; the database does not stop, for example, a `save` on a comment.

## users

**Prisma model:** `User`

One row per account.

| Column | Prisma field | Type | Null? | Default | Key / Constraint | Description |
|---|---|---|---|---|---|---|
| `id` | `id` | text (UUID) | No | `uuid()` | PK | Account id. Generated for now; may become, or be joined to, the auth provider's user id once one is chosen (see TODO.md). |
| `username` | `username` | text | No | — | Unique | Public handle. |
| `description` | `description` | text | Yes | — | | Profile bio. |
| `created_at` | `createdAt` | timestamp | No | `now()` | | When the account was created. |
| `updated_at` | `updatedAt` | timestamp | No | set by Prisma | | When the row was last updated. |

**Indexes & unique constraints**
- Unique on `username`.

**Relationships**
- Has many `posts` (`posts.user_id`). Delete: Restrict.
- Has many `comments` (`comments.user_id`). Delete: Restrict.
- Has many `reactions` as the author (`reactions.user_id`, relation `ReactionAuthor`). Delete: Restrict.
- Has many `reactions` as the follow target (`reactions.target_user_id`, relation `ReactionTargetUser`). Delete: Cascade.

Because posts, comments, and authored reactions use Restrict, the database rejects deleting any user who still has them.

**Deletion**
- Account deletion is not supported yet (post-MVP). Until it is built, the Restrict rules above block any user delete.
- The planned approach is a hard delete run by a single server function in one transaction: delete the user's posts (cascade clears everything under them), then their comments and reactions on other people's content with the matching count decrements, then the user row. There is no soft deletion. See README → Architecture Notes and TODO.md → Post-MVP.

## posts

**Prisma model:** `Post`

A user's post. The body is built from ordered `post_modules`; the post itself holds an optional caption, images, and cached counts.

| Column | Prisma field | Type | Null? | Default | Key / Constraint | Description |
|---|---|---|---|---|---|---|
| `id` | `id` | text (UUID) | No | `uuid()` | PK | Post id. |
| `user_id` | `userId` | text | No | — | FK → `users.id` (Restrict) | Author of the post. |
| `caption` | `caption` | text | No | `''` | | Optional caption. An empty string means no caption. |
| `images` | `images` | text[] | No | `[]` | | Image references (Cloudinary). An empty array means no images. |
| `like_count` | `likeCount` | integer | No | `0` | | Cached count of `like` reactions on this post. |
| `dislike_count` | `dislikeCount` | integer | No | `0` | | Cached count of `dislike` reactions on this post. |
| `save_count` | `saveCount` | integer | No | `0` | | Cached count of `save` reactions on this post. |
| `comment_count` | `commentCount` | integer | No | `0` | | Cached count of comments on this post. |
| `created_at` | `createdAt` | timestamp | No | `now()` | | When the post was created. |
| `updated_at` | `updatedAt` | timestamp | No | set by Prisma | | When the row was last updated. |

**Indexes & unique constraints**
- Index on `user_id` (for "posts by this user").

**Relationships**
- Belongs to one `users` row (author). Delete: Restrict.
- Has many `post_modules`. Deleting the post cascades to them.
- Has many `comments`. Deleting the post cascades to them (and, through them, to their reactions).
- Has many `reactions`. Deleting the post cascades to them.

**App-enforced rules**
- A post must have a non-empty `caption` **or** at least one entry in `images`.
- `like_count`, `dislike_count`, `save_count`, and `comment_count` must be updated in the same transaction as every insert or delete of the matching `reactions` / `comments` rows.

## post_modules

**Prisma model:** `PostModule`

One block of a modular post (text, checklist, video, etc.), ordered by `position`.

| Column | Prisma field | Type | Null? | Default | Key / Constraint | Description |
|---|---|---|---|---|---|---|
| `id` | `id` | text (UUID) | No | `uuid()` | PK | Module id. |
| `post_id` | `postId` | text | No | — | FK → `posts.id` (Cascade) | Post this module belongs to. |
| `module_type` | `moduleType` | `ModuleType` | No | — | | Kind of module. Determines the shape of `data`. |
| `position` | `position` | double precision | No | — | Unique with `post_id` | Sort order within the post. A float, so a module can be inserted between two others (e.g. `1.5`) without renumbering. |
| `data` | `data` | jsonb | No | — | | Module content. Shape depends on `module_type` (see below). |
| `created_at` | `createdAt` | timestamp | No | `now()` | | When the module was created. |
| `updated_at` | `updatedAt` | timestamp | No | set by Prisma | | When the row was last updated. |

**Indexes & unique constraints**
- Unique on (`post_id`, `position`). No two modules in a post can share a position. This index also serves "modules of this post, in order", so no separate index on `post_id` is needed.

**Relationships**
- Belongs to one `posts` row. Deleted when the post is deleted.

**`data` shapes by `module_type`** (validated at the app layer, e.g. with Zod)

| `module_type` | Shape of `data` | Notes |
|---|---|---|
| `text` | `{ body: string }` | |
| `checklist` | `{ items: [{ id, text, checked }] }` | |
| `numbered_list` | `{ items: [{ id, text }] }` | |
| `video` | `{ video_id: string }` | YouTube video id only (MVP). |
| `location` | `{ address?, longitude, latitude, label }` | `address` is optional. |
| `timer` | `{ hours, minutes, label? }` | `hours` 0–99, `minutes` 0–59, `label` optional. |

**App-enforced rules**
- `data` must match the shape for its `module_type`.

## comments

**Prisma model:** `Comment`

A comment left by a user on a post. A user can leave any number of comments on the same post.

| Column | Prisma field | Type | Null? | Default | Key / Constraint | Description |
|---|---|---|---|---|---|---|
| `id` | `id` | text (UUID) | No | `uuid()` | PK | Comment id. |
| `user_id` | `userId` | text | No | — | FK → `users.id` (Restrict) | Author of the comment. |
| `post_id` | `postId` | text | No | — | FK → `posts.id` (Cascade) | Post the comment is on. |
| `text` | `text` | text | Yes | — | | Comment text. |
| `image` | `image` | text | Yes | — | | Image reference (Cloudinary). |
| `like_count` | `likeCount` | integer | No | `0` | | Cached count of `like` reactions on this comment. |
| `dislike_count` | `dislikeCount` | integer | No | `0` | | Cached count of `dislike` reactions on this comment. |
| `created_at` | `createdAt` | timestamp | No | `now()` | | When the comment was created. |
| `updated_at` | `updatedAt` | timestamp | No | set by Prisma | | When the comment was last edited. |

**Indexes & unique constraints**
- Index on `post_id` (for "comments on this post").
- Index on `user_id` (for "comments by this user", e.g. a profile tab).

**Relationships**
- Belongs to one `users` row (author). Delete: Restrict.
- Belongs to one `posts` row. Deleted when the post is deleted.
- Has many `reactions`. Deleting the comment cascades to them.

**App-enforced rules**
- A comment must have `text` **or** `image` (at least one non-null).
- `like_count` and `dislike_count` must be updated in the same transaction as every insert or delete of the matching `reactions` rows.
- Creating or deleting a comment must update `posts.comment_count` in the same transaction.

## reactions

**Prisma model:** `Reaction`

One user reacting to one thing: a like, dislike, or save on a post; a like or dislike on a comment; or a follow of another user. Each row points at exactly one target.

| Column | Prisma field | Type | Null? | Default | Key / Constraint | Description |
|---|---|---|---|---|---|---|
| `id` | `id` | text (UUID) | No | `uuid()` | PK | Reaction id. |
| `user_id` | `userId` | text | No | — | FK → `users.id` (Restrict) | User who reacted (relation `ReactionAuthor`). |
| `type` | `type` | `ReactionType` | No | — | | Kind of reaction. |
| `post_id` | `postId` | text | Yes | — | FK → `posts.id` (Cascade) | Target post. Set only for reactions on a post. |
| `comment_id` | `commentId` | text | Yes | — | FK → `comments.id` (Cascade) | Target comment. Set only for reactions on a comment. |
| `target_user_id` | `targetUserId` | text | Yes | — | FK → `users.id` (Cascade) | User being followed (relation `ReactionTargetUser`). Set only when `type` is `follow`. |
| `created_at` | `createdAt` | timestamp | No | `now()` | | When the reaction was made. |
| `updated_at` | `updatedAt` | timestamp | No | set by Prisma | | When the row was last updated. |

**Indexes & unique constraints**

| Columns | Kind | Purpose |
|---|---|---|
| (`user_id`, `post_id`, `type`) | Unique | A user can't give the same reaction to the same post twice. |
| (`user_id`, `comment_id`, `type`) | Unique | A user can't give the same reaction to the same comment twice. |
| (`user_id`, `target_user_id`, `type`) | Unique | A user can't follow the same user twice. |
| (`post_id`, `type`) | Index | "Reactions of this type on this post." |
| (`comment_id`, `type`) | Index | "Reactions of this type on this comment." |
| (`target_user_id`, `type`) | Index | "Followers of this user." |

The unique constraints start with `user_id`, so they also serve "what has this user reacted to". The plain indexes start with the target, so they serve lookups from the post, comment, or user side.

In PostgreSQL, NULLs are never equal to each other in a unique constraint. Each unique constraint therefore only applies to rows where its target column is set. For example, a comment reaction has `post_id = NULL`, so only the `comment_id` constraint applies to it.

**Relationships**
- Belongs to one `users` row as the author. Delete: Restrict.
- Belongs to at most one of: a `posts` row, a `comments` row, or a `users` row as the follow target. Deleting that target cascades to the reaction.

**App-enforced rules**
- Exactly one of `post_id`, `comment_id`, `target_user_id` must be set. (Not enforced by the database. A row with none set would pass every unique constraint. This could be enforced with a `CHECK (num_nonnulls(post_id, comment_id, target_user_id) = 1)` constraint added by hand in a migration.)
- `type` must be valid for the target: `like` / `dislike` / `save` for posts, `like` / `dislike` for comments, `follow` for users.
- A user can currently hold both a `like` and a `dislike` on the same post or comment, since the types differ. If votes should be mutually exclusive, the app must remove the opposite vote in the same transaction.
- Inserting or deleting a reaction must update the matching `*_count` column on the target post or comment in the same transaction. Follows have no cached count.

## Relationship summary

| From | Column | To | On delete of target |
|---|---|---|---|
| `posts` | `user_id` | `users` | Restrict |
| `post_modules` | `post_id` | `posts` | Cascade |
| `comments` | `user_id` | `users` | Restrict |
| `comments` | `post_id` | `posts` | Cascade |
| `reactions` | `user_id` | `users` | Restrict |
| `reactions` | `post_id` | `posts` | Cascade |
| `reactions` | `comment_id` | `comments` | Cascade |
| `reactions` | `target_user_id` | `users` | Cascade |

```
users ──< posts ──< post_modules
  │         │
  │         └──< comments ──< reactions (comment_id)
  │         └──< reactions (post_id)
  ├──< comments (as author)
  ├──< reactions (as author, user_id)
  └──< reactions (as follow target, target_user_id)
```
